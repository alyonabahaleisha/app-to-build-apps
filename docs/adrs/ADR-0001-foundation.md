# ADR-0001: Foundation — Auth, DB Schema, Library Shell
*Authored by Cal — 2026-05-01*

## Status
Proposed

## Context

Robert's spec (`docs/product/app-creation-poc.md`) describes a slice that spans authentication, generation, persistence, render, and TestFlight ship. That's ~11 dev-days of work. Sable's UX doc (`docs/ux/app-creation-poc-ux.md`) and Robert's note both raised sub-slicing as a concern.

Three forces push toward sub-slicing:

1. **Dependency stratification.** Every authenticated route depends on `requireAuth`. Every project route depends on the `projects` schema. Every renderer test depends on a live spec. The work has natural seams.
2. **Risk concentration in the LLM call.** The riskiest piece — the Anthropic call with forced tool-use, schema validation, and ≥80% eval pass-rate — wants its own ADR with its own test gate. Bundling it with auth scaffolding lets implementation drift mask LLM regressions.
3. **TestFlight blocked on Apple Developer enrollment.** A 1-2 day external dependency we can't compress. The render+ship work should land in a final ADR so the others can proceed in parallel.

If we don't sub-slice, we ship a 14-day ADR with one merge gate. That's exactly the "big-bang" pattern the team's rules forbid.

> **What if we do nothing (don't write this ADR):** the engineer makes ad-hoc decisions on schema, auth, and routing while focusing on the LLM call. Six days later, we discover the renderer's state model conflicts with the auth context's React tree placement, and rework spans the whole app. That's the failure mode this ADR exists to prevent.

## Sub-slicing strategy (cross-ADR)

Three ADRs total for the App Creation POC slice. Each lands as an independent PR with its own test gate:

| ADR | Scope | Critical path? | Est. days |
|---|---|---|---|
| **0001 — this** | Auth, DB schema, projects service (read-only routes), mobile session hook, Sign-In + Home screens | Yes — blocks everything | 5 |
| **0002 — Generation** | LLM call + tool-use + spec validation + eval harness + Chat screen wiring | Depends on 0001 (uses `projectsService.create`) | 3 |
| **0003 — Render & Ship** | Full A2UI renderer (10 components), AppRunner, EAS production build, TestFlight submission | Depends on 0002 (specs to render) and on Apple Dev enrollment | 5 |

ADR-0002 and ADR-0003 will be drafted after 0001 lands — not preemptively. We learn things during 0001 that will sharpen 0002.

## Decision (this ADR)

Build the foundation: auth, persistence schema, the projects service (write API + read routes), and the mobile shell up to and including the empty Home screen. Ship to a working dev-client; auth flow demonstrable end-to-end.

### Architectural choices, with rationale and ARCHITECTURE.md citations

#### A. Postgres + Drizzle ORM (per ARCHITECTURE.md §0, §5, §14)
Tables defined in `services/api/src/db/schema.ts`. Migrations generated by `drizzle-kit` and committed alongside the schema diff. No raw SQL in route handlers. Connection pool via `pg.Pool` with bounded size; pool initialized in `services/api/src/db/index.ts` and consumed via dependency-injection-style import.

#### B. Supabase Auth for magic-link (per ARCHITECTURE.md §3, with §17 D1 caveat now resolved)
Server uses the `@supabase/supabase-js` admin client (service role key) to issue magic links. Client uses the Supabase auth API directly for the email-input + token-redemption flow. JWTs are validated server-side via `@fastify/jwt` against the `SUPABASE_JWT_SECRET` HS256 key. We do **not** delegate every authenticated request to Supabase — local JWT verification is faster and avoids per-request fan-out.

#### C. `requireAuth` Fastify hook (per CLAUDE.md §6)
A single Fastify decorator pre-handler: parses `Authorization: Bearer <jwt>`, verifies, attaches `req.user = {id, email}`. Returns 401 on missing or invalid JWT. Registered per route, not globally — health endpoint stays public.

#### D. Tokens stored in `expo-secure-store` only (per ARCHITECTURE.md §5, §17 red flag)
On the client, access + refresh tokens never touch AsyncStorage or MMKV. The session module wraps secure-store reads/writes; components access via `useSession()` and never see raw tokens.

#### E. Magic-link deep linking via `expo-linking` (per Sable's "Notes for Cal" #5)
URL scheme `appcreator://auth?token=...` matches `app.config.ts:scheme: 'appcreator'`. The `useURL()` hook handles cold-start (app launched from link tap) and warm-start (link tapped while app was backgrounded). Supabase redirect URL is configured in the dashboard, not in code.

#### F. React Context for session (per ARCHITECTURE.md §7, no global store)
A single `SessionProvider` mounted near the app root. Components read via `useSession()`. Refresh-token rotation lives inside the provider, exposed only as side effects from the hook — no manual refresh in feature code.

#### G. Mirror the Supabase user record into our `users` table (decision: own-user-table)
We could rely solely on Supabase's `auth.users` table. We don't, because we need referential integrity for `projects.owner_id` and the migration path to a non-Supabase auth provider stays open. On every sign-in, the server upserts the user into our local `users` table by Supabase's UUID (which is stable). Tradeoff: one extra DB write per session refresh — negligible.

#### H. Rate limiting per route, per user (Robert's AC-Q3, retro-lessons.md "CI/CD Pipeline Breakage")
30 requests / minute / user on every authenticated POST route. Implemented as a Fastify hook using an in-memory token bucket (no Redis at MVP — single API instance, fine for POC). Sized so a real user never hits it; a misbehaving client gets backpressure, not an incident.

#### I. Sign-In screen, Home screen, no Chat or AppRunner yet
The mobile shell renders Sign-In and Home (with empty library state, library list, and skeleton/error states). Chat and AppRunner come in ADR-0002 and ADR-0003 respectively. The navigator has stub routes for them so the linker doesn't break, but they render placeholder text.

#### J. Logger discipline from day 1 (per ARCHITECTURE.md §8)
Pino-based server logger. Email never logged at INFO. Tokens never logged. Structured fields only. The `safeMessage(err)` helper (already shipped in bootstrap) is used for every error log.

## Alternatives Considered

### Alternative 1: Self-host auth (Lucia, Auth.js, custom JWT)

- **Upside:** No vendor dependency. Full control over the email pipeline.
- **Downside:** Magic-link delivery is a real engineering job — bounce handling, expiry, SMTP relay, re-sending logic, inbox-deliverability tuning. We'd own all of it. Plus an ADR-0002 per provider when we add Apple sign-in in Phase 2.
- **Why not:** Two months of unbudgeted work for a PoC, on a feature surface that's table stakes everywhere else. Supabase eats this complexity for $0/month at our scale.

### Alternative 2: Clerk

- **Upside:** Best-in-class auth UX, drop-in components, generous free tier.
- **Downside:** Two SaaS vendors instead of one (Clerk for auth, Supabase for DB). Token-validation needs JWKS roundtrips or a second SDK. Migration cost if we ever leave is higher than Supabase because Clerk owns more user state.
- **Why not:** Supabase already provides Postgres + pgvector + auth in one project. Adding Clerk doubles the surface area without solving a problem we have.

### Alternative 3: Prisma instead of Drizzle

- **Upside:** Larger ecosystem, more documentation, schema-first dev experience, very polished migrations.
- **Downside:** Heavier runtime (the engine binary), slower cold start on serverless, extra tooling complexity. Drizzle is already in `ARCHITECTURE.md §14`.
- **Why not:** ARCHITECTURE.md sanctioned Drizzle. Switching now requires an ARCHITECTURE.md refresh and rewrites the schema patterns we'll use in 0002 and 0003. Not worth it for marginal DX upside.

### Alternative 4: Skip the local `users` mirror; FK to `auth.users.id`

- **Upside:** One less write per sign-in. Simpler.
- **Downside:** `auth.users` lives in the Supabase-managed `auth` schema. Cross-schema foreign keys work but couple our schema to Supabase's lifecycle (Supabase has changed `auth.users` shape historically). Migrating off Supabase becomes harder.
- **Why not:** A 1-write-per-session cost buys lifecycle independence. Worth it.

### Alternative 5: Bundle this with ADR-0002 and ADR-0003 into one ADR

- **Upside:** One PR, one merge.
- **Downside:** 11-day ADRs are how the "big-bang rewrite" failure mode shows up in our forbidden-action list. No checkpoint between auth and LLM means an LLM regression caught in QA forces a re-review of the auth code.
- **Why not:** Each 5-day ADR is an independent merge gate. Three of them is faster than one of fifteen with a 30% revisit rate.

## Consequences

### Positive

- Auth + DB live in production-shape from day 1. ADR-0002's `/generate` endpoint plugs in cleanly via `requireAuth` + `projectsService.create()`.
- Sign-In screen is shippable on its own — useful for stakeholder demos before generation works.
- `users` mirror keeps us provider-portable for Phase 2.

### Negative

- An ADR-0001 user can sign in but has no apps and no way to create one. The empty library is the *only* thing they can see. We need to accept this is the worst end-user demo state we'll ever ship — internal-only.
- Local `users` table introduces a potential drift point: if Supabase deletes a user from `auth.users`, our `users` row remains. Phase 2 needs a sync job. Documented under §17 known debt addition.
- Rate limiter is in-memory — won't survive multi-instance horizontal scale. Out of scope for POC; ARCHITECTURE.md §17 D9 added.

### Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Magic-link tap on iOS Simulator misroutes (browser opens, simulator doesn't catch the URL) | Medium | Step 6 includes a manual smoke test scenario. Documented workaround: `xcrun simctl openurl booted appcreator://auth?token=...` |
| Supabase JWT secret rotation breaks all sessions | Low | Document rotation runbook in §16 of ARCHITECTURE.md (Phase 2 follow-up — risk accepted for POC) |
| Drizzle migration fails on Supabase Postgres due to permission scoping | Low | Run migrations as the service-role-managed connection, not the public role. Verified in Step 1. |
| Race condition on `users` upsert at first sign-in | Low | Use `INSERT ... ON CONFLICT DO NOTHING RETURNING *` then re-SELECT. Tested in Step 4 concurrency tests. |
| `expo-secure-store` not available on iOS Simulator | Very low | Verified working on iOS Simulator since Expo SDK 47. Spike test in Step 5. |

**Code shape (signatures only):**
```ts
// services/api/src/db/schema.ts
export const users = pgTable('users', {
  id: uuid('id').primaryKey(),                           // matches Supabase auth.users.id
  email: text('email').notNull().unique(),
  createdAt: timestamp('created_at', {withTimezone: true}).notNull().defaultNow(),
})

export const projects = pgTable('projects', {
  id: uuid('id').primaryKey().defaultRandom(),
  ownerId: uuid('owner_id').notNull().references(() => users.id, {onDelete: 'cascade'}),
  title: text('title').notNull(),
  currentVersionId: uuid('current_version_id'),          // FK added in a later migration to break cycle
  parentProjectId: uuid('parent_project_id'),
  createdAt: timestamp('created_at', {withTimezone: true}).notNull().defaultNow(),
  updatedAt: timestamp('updated_at', {withTimezone: true}).notNull().defaultNow(),
}, (t) => ({
  ownerIdx: index('projects_owner_idx').on(t.ownerId, t.updatedAt.desc()),
}))

export const projectVersions = pgTable('project_versions', { ... })  // FK to projects.id
export const messages = pgTable('messages', { ... })
export const facts = pgTable('facts', { ... })
export const memoryEmbeddings = pgTable('memory_embeddings', { ... })  // vector(1536) column
export const events = pgTable('events', { ... })
```

**Acceptance criteria:**
- `pnpm --filter @app-creator/api db:generate` produces `migrations/0001_init.sql` deterministically.
- Running migration against an empty DB creates all 7 tables, all FK constraints, all indexes.
- Running migration twice is idempotent (no duplicate table errors).
- `db.select().from(users)` typechecks and returns the right TS shape.
- `pgvector` extension enabled by the migration: `CREATE EXTENSION IF NOT EXISTS vector;` runs first.
- The `projects.currentVersionId` self-referential cycle is broken via a deferred FK added in `0002_project_version_fk.sql` (a follow-up migration in the same step).

**Estimated complexity:** Medium

### Step 2: Supabase admin client + JWT validation middleware

**Files to create:**
- `services/api/src/lib/supabase.ts` — exports `supabaseAdmin` (service-role client)
- `services/api/src/lib/auth.ts` — exports `verifyJwt(token: string)`, `requireAuth` Fastify hook, `AuthenticatedRequest` type
- `services/api/src/lib/auth.test.ts` — middleware tests
- Update `services/api/src/lib/env.ts` — make `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_JWT_SECRET` required when `NODE_ENV !== 'test'`; tests inject mocks.

**Code shape:**
```ts
// services/api/src/lib/auth.ts
export interface AuthUser {
  id: string
  email: string
}

export async function requireAuth(req: FastifyRequest, reply: FastifyReply): Promise<void> {
  const header = req.headers.authorization
  if (!header?.startsWith('Bearer ')) return reply.code(401).send({error: 'unauthorized'})
  const token = header.slice(7)
  try {
    const payload = await verifyJwt(token)
    ;(req as AuthenticatedRequest).user = {id: payload.sub, email: payload.email}
  } catch {
    return reply.code(401).send({error: 'unauthorized'})
  }
}
```

**Acceptance criteria:**
- Valid JWT signed with `SUPABASE_JWT_SECRET` is accepted; `req.user` populated with `id` and `email`.
- Missing `Authorization` header → 401 `{error: 'unauthorized'}`. No body leaks (no token echo, no email).
- `Authorization: Bearer <invalid>` → 401 `{error: 'unauthorized'}`.
- Expired JWT → 401 `{error: 'unauthorized'}`.
- JWT signed with the wrong key → 401 `{error: 'unauthorized'}`.
- `req.user.email` is never logged at INFO via `req.log.info`. Validated by grep + a log-spy unit test.

**Estimated complexity:** Low

### Step 3: Magic-link routes (POST /auth/magic-link, POST /auth/sync)

**Files to create:**
- `services/api/src/routes/auth.ts` — two routes
- `services/api/src/routes/auth.test.ts`
- `services/api/src/services/auth.service.ts` — thin wrapper around supabaseAdmin
- `services/api/src/services/users.service.ts` — `findOrCreate(supabaseUserId, email)`

**Code shape:**
```ts
// POST /auth/magic-link {email} → {sent: true} (200) or {error} (400/500)
// Triggers Supabase to send a magic-link email. We do not return any token.

// POST /auth/sync — used by the client after magic-link redemption.
// Header: Authorization: Bearer <supabase-issued-jwt>
// Body: empty
// Returns: {user: {id, email}}  — confirms server-side mirror exists.
// preHandler: requireAuth
```

**Why a `/auth/sync` step (vs. just relying on the JWT):**
The JWT carries `sub` (Supabase user UUID) and `email`. We need a server-side row in our `users` table for `projects.owner_id` FK integrity. `/auth/sync` is the explicit contract for "mirror this user," called once per session start. Deterministic, debuggable.

**Acceptance criteria:**
- `POST /auth/magic-link {email: 'user@example.com'}` calls `supabaseAdmin.auth.admin.generateLink({type: 'magiclink', email})` and returns `{sent: true}` on success.
- Email validation: must contain `@` and a `.` after it; otherwise 400 `{error: 'invalid_input', detail: 'email format'}`.
- Supabase API failure → 500 `{error: 'internal'}`. The Supabase error message is logged via `safeMessage` but not returned to the client.
- `POST /auth/sync` with valid JWT inserts the user row if absent (`INSERT ... ON CONFLICT (id) DO NOTHING`); returns `{user: {id, email}}` either way.
- `POST /auth/sync` without auth → 401.
- Two concurrent `POST /auth/sync` calls for the same user (race) result in exactly one row. Verified by a transaction-isolation test.

**Estimated complexity:** Medium

### Step 4: Projects service (internal API) + read-only routes

**Files to create:**
- `services/api/src/services/projects.service.ts` — `create`, `list`, `get`
- `services/api/src/services/projects.service.test.ts`
- `services/api/src/routes/projects.ts` — `GET /projects`, `GET /projects/:id`
- `services/api/src/routes/projects.test.ts`
- `services/api/src/lib/canonical.ts` — re-exports `canonicalize` and `renderHash` from `@app-creator/a2ui-schema/canonical` for server-side use

**Code shape:**
```ts
// services/api/src/services/projects.service.ts

import {A2UISpec, A2UISpecSchema} from '@app-creator/a2ui-schema'
import {renderHash} from '@app-creator/a2ui-schema/canonical'

export type CreateProjectInput = {
  ownerId: string
  spec: A2UISpec
  parentProjectId?: string
}

export type ProjectListItem = {
  id: string
  title: string
  updatedAt: string  // ISO
  currentVersionId: string
}

export type ProjectDetail = {
  project: {id: string; title: string; ownerId: string; createdAt: string; updatedAt: string}
  currentVersion: {id: string; specJson: A2UISpec; renderHash: string; createdAt: string}
}

export const projectsService = {
  async create(input: CreateProjectInput): Promise<ProjectDetail> { ... },     // auth-only
  async list(ownerId: string): Promise<ProjectListItem[]> { ... },             // auth-only, scoped
  async get(ownerId: string, projectId: string): Promise<ProjectDetail | null> { ... },  // auth-only, must be owner
}
```

`create()` runs in a transaction:
1. Validate spec via `A2UISpecSchema.parse(spec)` — throws on invalid.
2. Compute `renderHash`.
3. Derive title: first Heading text in the spec's first view, fallback "Untitled".
4. INSERT into `projects` with `current_version_id = null`.
5. INSERT into `project_versions` with `project_id = <new-project-id>`.
6. UPDATE `projects.current_version_id`.
7. Return `ProjectDetail`.

**Acceptance criteria:**
- `projectsService.create({ownerId, spec})` writes one project + one version row in a single transaction. If step 5 fails, step 4 rolls back.
- Title auto-derivation: spec with `{type: 'Heading', text: 'My App'}` as first node → `title: 'My App'`. Spec with no Heading → `title: 'Untitled'`. Spec with Heading text > 60 chars → truncated to 60 + ellipsis.
- `projectsService.list(ownerId)` returns the user's projects sorted by `updated_at DESC`. Other users' projects never returned.
- `projectsService.get(ownerId, projectId)` returns the project if owned; returns `null` otherwise.
- `GET /projects` returns 200 `{projects: [...]}` for the authenticated user.
- `GET /projects/:id` returns 200 `{project, currentVersion}` for the owner; 404 `{error: 'not_found'}` for non-owners (we return 404, not 403 — don't leak existence of other users' projects).
- Project list endpoint excludes `spec_json` from the response (only the detail endpoint returns it). Per retro-lessons.md `normalizeRow` lesson: `auth-only` data scoping enforced explicitly.
- Concurrent `create()` calls for the same user produce two distinct projects with no FK violation.

**Estimated complexity:** Medium

**Acceptance criteria:**

**Code shape — deep link handler:**
```ts
// apps/mobile/src/lib/deepLink.ts
export function useAuthDeepLink() {
  const url = Linking.useURL()
  const {redeemToken} = useSession()

  useEffect(() => {
    if (!url) return
    const parsed = Linking.parse(url)
    if (parsed.scheme === 'appcreator' && parsed.hostname === 'auth') {
      const token = parsed.queryParams?.token
      if (typeof token === 'string') {
        redeemToken(token)
      }
    }
  }, [url, redeemToken])
}
```

**Acceptance criteria** (drives Sable's UX states from `docs/ux/app-creation-poc-ux.md` §Screen 1):

- "Resend" available after 30s cooldown.
- Server error → toast with copy from §Content & Copy: "Couldn't send the link. Try again in a moment."
- Tapping a link in Mail (simulator: `xcrun simctl openurl booted appcreator://auth?token=...`) opens the app, calls `useAuthDeepLink()`, redeems, and the user is signed in.
- Expired/used token → Sign-In screen with banner: "That link expired. Send a new one?"

## Notes for Colby

Tactical reminders that come up during implementation:

1. **Drizzle's `pgvector` integration** is via `drizzle-orm/pg-core` + the `vector` column type. The `0001_init.sql` migration must include `CREATE EXTENSION IF NOT EXISTS vector;` at the top. Drizzle won't add this; you do.
2. **Self-FK cycle** between `projects.current_version_id → project_versions.id` and `project_versions.project_id → projects.id`: the cleanest pattern is to define `current_version_id` as nullable in `0001_init.sql`, then add the FK constraint in `0002_project_version_fk.sql` once both tables exist. If Drizzle migrations don't naturally produce this split, write the second migration by hand and commit it.
3. **The `requireAuth` decorator pattern in Fastify v5** uses `preHandler` arrays per route, not a global hook — keep it explicit so the `/health` route doesn't accidentally inherit auth.
4. **`expo-secure-store` on iOS Simulator** *does* work since SDK 47, but the Keychain access group needs to be the default (don't set `keychainAccessGroup` in your secure-store calls — you don't need it for this scope). Confirmed.
5. **`expo-linking`'s `useURL()` hook returns the same URL across re-renders until a new deep-link arrives.** Don't call `redeemToken()` on every render — the `useEffect` dependency array on `[url, redeemToken]` is correct, but make sure `redeemToken` is stable (wrap in useCallback or read from a ref).
6. **Testing magic-link redemption on simulator** — use `xcrun simctl openurl booted appcreator://auth?token=foo` to fire the deep link from the terminal. Don't rely on actually sending an email during dev tests.
7. **The `Toast` component** — use a portal-style provider mount, not a per-screen render. Sable's spec implies a single toast at a time, dismissible by tap. Queue policy: replace the current toast with the new one (don't stack).
8. **For light/dark theming** — set up the theme tokens in `apps/mobile/src/theme/` and use `useColorScheme()` from React Native to drive a `ThemeProvider`. Don't rely on `useColorScheme()` directly in components — gate it through the provider so we can override for testing and (Phase 2) manual user toggle.
9. **Bear hug rule on imports**: every file at `apps/mobile/src/**` uses the `#/` alias for in-workspace imports. The Babel `module-resolver` plugin is already set up. If TypeScript complains about `#/...` resolution, check the `paths` in `apps/mobile/tsconfig.json`.
10. **The placeholder Chat and AppRunner screens** for this ADR are literally just `<Text>Coming soon</Text>` inside a `SafeContainer`. Don't gold-plate them — they get replaced wholesale in ADR-0002 and ADR-0003.
